How to define a CDE for the engine

The Critical Data Element tells the engine which Athena table and column to check. This page covers each CDE field from the engine's perspective — what it does and when it is required.

CDE field reference

When the engine processes a rule allocation, it looks up the linked CDE and uses these fields to build and execute the SQL.

FieldRequiredDescription
critical_data_element_id required Unique identifier for this CDE. Referenced by rule allocations.
critical_dataset_id required The parent Critical Data Set this CDE belongs to.
source_database_name required The Athena database name. Substituted into the rule SQL wherever {SOURCE_DATABASE_NAME} appears.
source_table_name required The Athena table name. Substituted into the rule SQL wherever {SOURCE_TABLE_NAME} appears.
source_field_name automated rules only The column to check. Substituted into the rule SQL wherever {SOURCE_FIELD_NAME} appears. Leave blank for manual rules or rules that do not reference a specific column.
source_snapshot_filter optional A SQL predicate that pins the check to the most recent data load. Applied to both the failures query and the denominator query. See below.
retiring_timestamp optional Set to a past timestamp to deactivate this CDE. Leave blank to keep the CDE active. When retired, all rule allocations linked to this CDE are also excluded from runs.

The snapshot filter

Many source tables accumulate multiple data loads over time — daily extracts, monthly snapshots, or SCD history. Without a snapshot filter, a rule would evaluate every row in the table, mixing current and historical records.

The snapshot filter is a SQL WHERE clause fragment that identifies which rows represent the current picture. The engine appends it to your rule SQL as AND {filter} after snapshot filter injection, so your rule SQL must always have an outer WHERE clause when a filter is set.

The snapshot filter is shared between the failures query and the denominator query. Both measure the same slice of data, so the pass rate is meaningful rather than comparing different record populations.

The filter value can use the same {SOURCE_DATABASE_NAME} and {SOURCE_TABLE_NAME} placeholders as the rule SQL. These are substituted before the filter is appended.

Example filter value:

glueexporteddate = (SELECT MAX(glueexporteddate) FROM {source_database_name}.{source_table_name})

For guidance on identifying the right filter value for a CDE, see What is a snapshot filter?

source_field_name — when it is required

This field is only needed when the rule SQL contains the {SOURCE_FIELD_NAME} placeholder. Rules that check table-level conditions (row counts, date ranges across the whole table) do not need it. Rules that check a specific column — null checks, format checks, allowed-value checks — do.

  • For manual rules: leave blank. The SQL for a manual rule points at an upload table and does not reference individual source columns.
  • For automated rules that use {SOURCE_FIELD_NAME}: the field must be populated or the substitution will produce invalid SQL.
The three source fields (database, table, field) are substituted as double-quoted Athena identifiers. You do not need to add quotes in the CDE — the engine adds them automatically during placeholder substitution.
