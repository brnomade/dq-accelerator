How the engine processes a rule

What happens between the moment the engine picks up a rule from the metadata tables and the moment a measurement row is written.

Processing pipeline — automated rules

Each automated rule's SQL passes through the following steps in sequence. A failure at any step skips that rule; the remaining rules continue.

  1. 1
    Unicode cleaning — invisible characters, control codes, and non-standard spaces are stripped from the rule SQL before any other processing begins.
    This handles common artefacts from copy-pasting SQL out of spreadsheet tools.
  2. 2
    Snapshot filter injection — if the rule's CDE has a source_snapshot_filter defined, it is appended to the SQL as AND {filter}. This happens before normalisation and placeholder substitution.
    This is why your SQL must have an outer WHERE clause when a snapshot filter is set — the engine has no WHERE keyword to attach AND to otherwise.
  3. 3
    Normalisation — leading and trailing whitespace is trimmed, trailing semicolons are stripped, and newlines are flattened to single spaces.
  4. 4
    Placeholder substitution — {SOURCE_DATABASE_NAME}, {SOURCE_TABLE_NAME}, and {SOURCE_FIELD_NAME} are replaced with the actual values from the CDE row, wrapped in double-quotes.
    For example, {SOURCE_TABLE_NAME} becomes "contacts". Both uppercase and lowercase placeholder forms are handled.
  5. 5
    Safety check — the resulting SQL is validated against the engine's safety rules. If rejected, a blocked audit row is written and the rule is skipped. The run continues with the next rule.
    See SQL safety rules for the full list of what is and is not permitted.
  6. 6
    Execution — the failures SQL and the denominator SQL are each executed as a single scalar count against Athena. The results are combined and written as one measurement row.

The denominator (sample count)

The denominator counts the total records in scope. The engine determines it one of two ways:

  • If the rule has a Denominator Counter value set, that SQL is processed through the same pipeline (steps 1, 3, 4, 5) and executed as the denominator.
  • Otherwise, the engine automatically generates SELECT COUNT(*) FROM "database"."table", applying the snapshot filter as a WHERE clause if one is defined.

The engine-generated denominator is not passed through the safety validator because it is authored by the engine itself.

Processing pipeline — manual rules

Manual rules follow a shorter path. The engine applies the same clean, normalise, substitute, and safety-check steps (steps 1, 3, 4, 5 above), then:

  • Appends a freshness filter based on the last successful run for that allocation. Only rows with an extraction_timestamp newer than the last successful run are retrieved. On the first run for an allocation, all rows are ingested.
  • Returns one measurement row per qualifying uploaded row — not a single aggregate.

What the audit table records

Every rule — whether it ran successfully or was blocked — produces an audit row. The audit row contains the compiled SQL (post-substitution), whether the rule was blocked, and the reason if it was. You can use the audit table to inspect exactly what SQL the engine tried to run and why a rule was skipped.

FieldDescription
compiled_sqlThe SQL after all substitutions — this is what the engine actually submitted or attempted to submit.
is_blockedtrue if the rule did not execute; false if it ran.
blocked_reasonThe validation message or runtime error for blocked rules; null for rules that ran successfully.
rule_typeautomated or manual.

When a rule is blocked

A rule can be blocked at step 5 (safety validation fails) or at step 6 (a runtime error occurs in Athena, such as a table not found or a permission denied). In both cases:

  • An audit row is written with is_blocked = true and the reason recorded in blocked_reason.
  • No measurement row is written for that rule.
  • The engine moves on to the next rule — the rest of the run is not affected.
If you notice a rule is not producing measurements, check the audit table for its most recent row. The blocked_reason field will tell you exactly what the engine rejected and why.

Rule filtering

Before processing begins, the engine filters out rules that do not qualify for the current run:

  • Rules, allocations, or CDEs with a retiring_timestamp in the past are excluded.
  • Allocations whose frequency does not match the requested schedule are excluded.
  • If the run is scoped to a specific agency, only rules belonging to that agency are included.
