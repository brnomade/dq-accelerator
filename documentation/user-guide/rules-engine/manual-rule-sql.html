How to write SQL for manual rules

Manual rules read pre-computed metrics from an upload table rather than executing a check directly against source data. Use this pattern when the DQ logic is too complex for a single SQL count, or when measurements originate from an external system.

When to use a manual rule

Use a manual rule when:

  • The DQ check requires complex logic that cannot be expressed as a single SELECT COUNT(*).
  • Measurements are produced by a process outside Athena and uploaded separately.
  • The metric is calculated by the data engineering team or an external tool and the results are loaded into an upload table via the MoJ Data Uploader.

For straightforward column-level or table-level checks that can be expressed as a count, use an automated rule instead.

Required output columns

A manual rule's SQL must return exactly these four columns. The engine reads them directly and does not generate any additional counts.

ColumnTypeFormat
failures_count required Numeric Integer or decimal. The count of records that failed the check.
total_sample_count required Numeric Integer or decimal. The total records in scope (denominator).
measurement_timestamp required String DD/MM/YYYY — the date the metric was measured.
extraction_timestamp required String YYYYMMDDHHmmssZ — for example, 20251201143000Z. Used by the engine to filter for rows uploaded since the last successful run.

SQL format

The rule SQL points at the upload table that contains the pre-computed metrics for this rule. Use the same {SOURCE_DATABASE_NAME} and {SOURCE_TABLE_NAME} placeholders as automated rules — these are substituted from the linked CDE.

SELECT failures_count, total_sample_count, measurement_timestamp, extraction_timestamp FROM {source_database_name}.{source_table_name}

Each manual rule has its own dedicated upload table — there is no shared global feed. The CDE for a manual rule should point at the upload table specific to that rule.

The extraction_timestamp column

The engine uses extraction_timestamp to deduplicate on each run: it only ingests rows with an extraction_timestamp newer than the last successful run for that allocation. This means:

  • Old rows remain in the upload table safely — they will not be re-ingested.
  • On the first run for an allocation (no prior successful run), all rows are ingested once.
  • If a run fails partway through, the next run re-ingests from the same timestamp boundary, not from a later one.
The extraction_timestamp column is added automatically by the MoJ Data Uploader when metrics are uploaded. You do not need to include it in the upload file itself — but your rule SQL must select it by name as shown above.

Schedule requirement

Manual rules must have their allocation frequency set to ad-hoc. They are triggered in a separate run from automated rules.

ad-hoc cannot be combined with other schedule values. A run that includes ad-hoc alongside hourly, daily, or weekly will be rejected by the engine before any rules are processed.
