SQL safety rules

Before execution, every rule SQL is validated. Rules that fail the check are skipped and an audit record is written — they do not stop the rest of the run.

What the engine blocks

A rule is blocked and logged if its SQL:

  • BLOCKEDDoes not start with SELECT. Leading comments are not allowed. The first non-whitespace characters must be SELECT.
  • BLOCKEDContains a semicolon outside string literals. Only single statements are permitted. A semicolon inside a string literal (e.g. WHERE note = 'call at 3;30pm') will also be rejected — rewrite the literal to avoid it.
  • BLOCKEDContains any of the following as standalone tokens: INSERT, UPDATE, DELETE, MERGE, DROP, TRUNCATE, ALTER, CREATE.
  • BLOCKEDUses a CTE (WITH … AS (…)). CTEs are not currently supported. Rewrite CTE logic as a subquery instead (see below).

Additional validation rules

Beyond the structural rules above, the engine also validates the shape and safety of the query to ensure it produces a single count and does not expose raw data:

  • The outermost SELECT must return a single numeric value from an aggregate function (COUNT, SUM, or APPROX_DISTINCT). MAX and MIN are permitted only when their result is consumed by a comparison (for example, inside a CASE WHEN MAX(date_col) < CURRENT_DATE expression — not returned bare).
  • No SELECT * or multi-column projections in the outermost SELECT.
  • No GROUP BY in the outermost SELECT.
  • No CROSS JOIN or implicit comma joins. All joins must have explicit ON or USING conditions with column references.
  • No access to information_schema, system, or other metadata catalogs.
  • No UNION at the outermost level. UNION ALL inside a FROM-clause derived table is permitted (see below).
  • No WITH RECURSIVE (recursive CTEs).
  • At most 5 tables directly joined within a single FROM / JOIN chain. Pre-aggregated subqueries that each reference one table do not count against this limit.
  • Partition filters must be present for any table registered as partitioned in the engine configuration.

CTEs are not supported — use subqueries

Queries that start with WITH are blocked because they do not start with SELECT. Rewrite the same logic as a subquery in the FROM clause:

Blocked — starts with WITH, not SELECT
WITH recent AS ( SELECT * FROM {SOURCE_DATABASE_NAME}.{SOURCE_TABLE_NAME} WHERE snapshot_date = (SELECT MAX(snapshot_date) FROM {SOURCE_DATABASE_NAME}.{SOURCE_TABLE_NAME}) ) SELECT COUNT(*) FROM recent WHERE {SOURCE_FIELD_NAME} IS NULL
Allowed — same logic as an inline subquery
SELECT COUNT(*) FROM ( SELECT * FROM {SOURCE_DATABASE_NAME}.{SOURCE_TABLE_NAME} WHERE snapshot_date = (SELECT MAX(snapshot_date) FROM {SOURCE_DATABASE_NAME}.{SOURCE_TABLE_NAME}) ) WHERE {SOURCE_FIELD_NAME} IS NULL

UNION ALL in subqueries

UNION ALL is permitted when it appears inside a FROM-clause derived table (an inline subquery). It is not permitted inside a CTE body or at the outermost level.

Allowed — UNION ALL inside a FROM-clause derived table
SELECT COUNT(*) FROM ( SELECT id FROM {SOURCE_DATABASE_NAME}.table_a WHERE status = 'failed' UNION ALL SELECT id FROM {SOURCE_DATABASE_NAME}.table_b WHERE status = 'failed' ) WHERE 1=1

What happens when a rule is blocked

When a rule fails the safety check:

  • No measurement row is written for that rule.
  • An audit row is written with is_blocked = true and the rejection reason in blocked_reason.
  • The engine moves on to the next rule — the rest of the run is unaffected.
To diagnose a blocked rule, look up its most recent entry in the compiled SQL audit table. The blocked_reason field will identify which rule it failed and why. The compiled_sql field shows the post-substitution SQL the engine attempted to validate — this is often more useful for debugging than the original template.
