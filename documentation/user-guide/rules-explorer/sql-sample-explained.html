When to use the SQL sample field

The SQL sample field is a specialist override for the denominator of the failure rate calculation. It is left blank for the vast majority of rules.

How failure rate is calculated

Every data quality rule produces a failure rate: the proportion of records in scope that fail the check. The calculation has two parts:

Standard formula
Failure rate = sql_code result (count of failing records)
                  ÷ universe (COUNT(*) WHERE snapshot_filter)

The universe is the total number of rows in scope for the rule. By default, this is a plain COUNT(*) filtered only by the CDE's snapshot filter — meaning every live row in the table is considered a candidate.

This works correctly for rules that apply to every row in the table. Most rules fall into this category.

When the default universe is wrong

Some rules are intentionally bounded to a subset of rows beyond what the snapshot filter covers. The failure count only looks at those rows — but if the denominator is still the full table, the failure rate is artificially diluted and meaningless.

Example: a date-bounded rule

A rule checks that every prisoner record created in the past 10 days has a case worker assigned.

sql_code counts failures only among records where created_date >= today - 10 days.

If the table holds 50,000 records but only 200 were created in the last 10 days, dividing by 50,000 produces a near-zero rate that tells you nothing about the actual problem.

The correct denominator is the count of the same 200 recent records — not the full table.

This is the only scenario where the SQL sample field is needed.

What to put in the SQL sample field

The SQL sample field must contain a COUNT(*) query that applies the same bounding condition as the rule SQL, in addition to the snapshot filter. It replaces the default full-table count as the denominator.

Correct sql_code_sample for the example above
SELECT COUNT(*) FROM {table} WHERE {snapshot} AND created_date >= DATEADD(day, -10, GETDATE())

The bounding condition matches the one in sql_code exactly. The snapshot token ensures both queries operate on the same base population.

Rules for the SQL sample field
• Must be a COUNT(*) query — not a row-level SELECT.
• Must include the snapshot filter token ({snapshot}) plus the same bounding condition as sql_code.
• Never use LIMIT — this is a count of the universe, not a sample of rows.
• Leave blank for any rule that checks all rows in the snapshot. That is the common case.

AI-generated rules

When the DQ Assistant generates a rule, it sets sql_code_sample to null unless it detects that the rule SQL is bounded to a subset. If you review an AI-generated rule and notice the failure rate looks wrong in production, check whether the rule has a bounding condition that the default universe does not cover, and add a sql_code_sample manually via the edit panel in the Rules Explorer.
